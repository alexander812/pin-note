# PinNote на любом проекте

PinNote — не расширение для браузера. Он поднимает собственный сервер на `127.0.0.1:4174` и умеет работать в двух режимах:

- **статический** — раздаёт папку со сборкой;
- **прокси** — подключается к уже запущенному dev-серверу (Vite, Next, Astro и т. п.), вставляет свой клиент в проксируемый HTML и пробрасывает WebSocket/HMR. Адрес можно указать через `--target` или дать PinNote найти запущенный dev-сервер по папке проекта.

В обоих случаях цикл одинаковый:

1. Получить страницу: собрать статику или запустить dev-сервер.
2. Запустить PinNote на папку сборки или на корень проекта: запущенный dev-сервер найдётся автоматически, а `--target` задаёт адрес вручную.
3. Оставить комментарии в браузере.
4. Попросить агента разобрать `.review/comments.json`.
5. Проверить результат: в статическом режиме пересобрать проект, в режиме прокси — дождаться HMR.

Короткая версия для проекта со сборкой в `dist`:

```bash
cd ~/p/project
npm run build
pin-note dist --source-dir . --data-dir ./.review
```

Короткая версия для запущенного dev-сервера:

```bash
cd ~/p/project
npm run dev

# в другом терминале
pin-note .
```

Если автоопределение не сработало, укажи адрес явно: `pin-note . --target http://localhost:5173`. Если dev-сервера нет и нужна статика, добавь `--no-detect`.

Здесь и ниже команда `pin-note` предполагает alias из следующего раздела. Без него используй `node "$HOME/p/pin-note/bin/pin-note.mjs"`.

Дальше — подробности.

## 1. Подготовка (один раз)

Нужен Node.js 20+.

Чтобы не писать полный путь к PinNote каждый раз, добавь alias в `~/.zshrc` или `~/.bashrc`:

```bash
alias pin-note='node "$HOME/p/pin-note/bin/pin-note.mjs"'
```

Альтернатива — поставить команду в `PATH`:

```bash
cd ~/p/pin-note
npm link
```

После этого везде ниже можно использовать `pin-note` вместо длинного пути.

В `.gitignore` целевого проекта добавь:

```text
.review/
```

Так комментарии и служебные файлы review не попадут в коммит. Если хочешь хранить отзывы вместе с кодом — не добавляй.

### Что считается проектом

Проект — это каталог, который передан PinNote первым аргументом. По умолчанию данные лежат в `<этот каталог>/.review`, а в `--target`-режиме оттуда же берутся подсказки по исходникам. Поэтому:

- запускай PinNote из корня проекта или передавай путь явно;
- не запускай `pin-note . --target ...` из папки самого PinNote — иначе `.review` станет общим для всех проектов;
- не передавай один и тот же `--data-dir` разным проектам без необходимости.

Внизу панели комментариев видны имя проекта и фактический путь к `comments.json` — это быстрый способ проверить, что открыт нужный проект.

## 2. Статический режим: какую папку раздавать

Этот раздел нужен, если PinNote запускается на папку со сборкой. Если в этой папке найден запущенный dev-сервер, PinNote автоматически переключится в режим прокси; чтобы принудительно раздавать статику, добавь `--no-detect`. Для явного `--target` переходи к разделу 6.

| Проект | Сборка | Папка для PinNote |
| --- | --- | --- |
| Обычный статический сайт | не нужна | корень проекта |
| Vite (React, Vue, Svelte) | `npm run build` | `dist` |
| Create React App | `npm run build` | `build` |
| Next.js со static export | `npm run build` с `output: 'export'` | `out` |
| Astro | `npm run build` | `dist` |
| Nuxt | `npm run generate` | `.output/public` |
| SvelteKit с adapter-static | `npm run build` | `build` |

Для проекта со сборкой:

```bash
cd ~/p/project
npm run build

pin-note dist \
  --source-dir . \
  --data-dir ./.review
```

Замени `dist` на папку из таблицы. Что делают опции:

- `--source-dir .` — искать подсказки по исходникам в корне проекта, а не в собранных файлах. Без этого `sourceHints` будут бесполезны.
- `--data-dir ./.review` — хранить `comments.json` и `feedback.md` в корне проекта. Тогда отзывы переживут пересборку, которая часто очищает `dist`.
- `--spa` — добавить, если у приложения клиентский роутинг (React Router, Vue Router, SvelteKit SPA). Тогда прямые ссылки на внутренние маршруты будут отдавать `index.html`.

Если сайт статический и сборки нет:

```bash
cd ~/p/site
pin-note .
```

В этом случае `--source-dir` и `--data-dir` можно не указывать: по умолчанию PinNote ищет исходники в той же папке и складывает `.review` туда же.

Относительные пути в `--data-dir` и `--source-dir` считаются от текущей папки терминала, поэтому запускай команду из корня проекта.

После старта PinNote напечатает адрес:

```text
Review: http://127.0.0.1:4174
```

Открывай именно его, а не адрес dev-сервера. Если порт 4174 занят, PinNote без явного `-p` попробует следующие порты и покажет фактический адрес в терминале.

## 3. Как оставлять комментарии

1. Открой адрес, который напечатал PinNote. Браузер откроется сам, если запуск был из терминала.
2. В правом нижнем углу нажми **«Комментировать»**. Включится режим review.
3. Наведи курсор на элемент: он подсветится рамкой и подписью с тегом.
4. Кликни по элементу. Откроется поповер с якорем: селектор, тег и текст элемента.
5. Напиши комментарий и нажми **⌘↵** (macOS) или **Ctrl+Enter** (Windows/Linux). **Esc** закрывает поповер без сохранения.
6. Если попал не в тот элемент, кликни с зажатым **Alt** (на Mac — **Option**): будет выбран родительский элемент. Повторный Alt/Option+клик поднимает ещё выше по дереву. Поповер при этом остаётся открытым, а уже введённый текст сохраняется.

Дальше:

- На странице появляются пины, а в панели **«Комментарии»** — список с фильтрами «Все», «Открытые», «Решённые». Выбранный фильтр применяется и к списку, и к пинам на странице: при «Открытых» остаются только нерешённые, при «Решённых» — только решённые.
- Клик по пину или по карточке прокручивает страницу к элементу и подсвечивает его.
- Кнопка **«Решить»** переводит комментарий в `resolved`, **«Вернуть»** — обратно в `open`.
- **«Копировать»** копирует один комментарий в Markdown, **«Скопировать для агента»** — весь список. Это удобно, если не хочешь давать агенту доступ к файлам.
- Панель можно перетащить за ручку `⠿`, если она закрывает интерфейс.
- Режим review не мешает переходить по страницам сайта: у каждого комментария сохраняется URL.

### Скриншот с пометками

В поповере комментария есть кнопка **«Скриншот элемента»**:

1. Нажми её и выбери **вкладку с сайтом** (не окно и не весь экран).
2. PinNote скроет свою панель, сделает кадр и обрежет его по выбранному элементу.
3. На открывшемся холсте рисуй линии мышью или пальцем; цвет выбирается из семи вариантов.
4. **«Отменить»** убирает последнюю линию, **«Очистить»** — все линии.
5. **«Прикрепить»** добавляет скриншот к комментарию. Перед сохранением его можно убрать крестиком.

Скриншот сохраняется в `.review/screenshots`, а в `comments.json` появляется поле `screenshot.file`. Агент увидит путь и изображение с пометками. Захват работает только при открытом review-сервере и в secure context (`localhost`/`127.0.0.1`).

Ограничение: сейчас захватывается выбранный элемент и его видимая часть. Скриншот всей страницы или произвольной области не поддерживается.

Комментарии сохраняются сразу на диск:

```text
.review/comments.json   источник правды
.review/feedback.md     человекочитаемая версия, генерируется сервером
.review/AGENT.md        краткая памятка для агента
.review/screenshots/    PNG-скриншоты с пометками
```

Внизу панели показаны имя проекта и путь к `comments.json` — по ним видно, какой проект сейчас открыт.

`feedback.md` вручную не редактируй: при следующем изменении сервер перезапишет его из `comments.json`.

Пока идёт review, терминал с PinNote не закрывай: сервер пишет комментарии и отдаёт страницу.

## 4. Как подключить агента

Агент должен работать в репозитории проекта и видеть `.review/comments.json`. Достаточно попросить:

```text
Разбери открытые комментарии из .review/comments.json.

Для каждого комментария со статусом open:
- найди исходник по anchor.selector, anchor.text, anchor.html и sourceHints;
- если есть screenshot.file, открой изображение относительно .review и учти пометки;
- внеси минимальную правку, не затрагивая несвязанные части;
- после проверки поставь status "resolved" и заполни resolution.

Если элемент не найден — поставь status "orphaned" и объясни причину в resolution.
Если правка не нужна — "wontfix" и объяснение.
Не удаляй комментарии и не меняй чужие поля.

После правок пересобери проект той же командой, которой он собирался для review.
```

Если `--data-dir` указывает в другое место, замени путь в промпте на фактический. В режиме прокси (`--target` или автоопределение) последнюю строку промпта можно заменить на «После правок ничего пересобирать не нужно: dev-сервер применит изменения через HMR».

Что происходит дальше:

1. Агент читает якоря и правит исходники, а не собранные файлы.
2. В статическом режиме агент пересобирает проект; в режиме прокси изменения подхватывает dev-сервер.
3. PinNote перезагружает вкладку при изменении статической сборки, а в режиме прокси это делает HMR dev-сервера.
4. Сервер следит за `comments.json` и обновляет статусы в панели.

Если вкладка не перезагрузилась сама, обнови её вручную. Если статусы не появились, нажми **«Обновить»** в панели.

`feedback.md` генерируется из `comments.json`; если он почему-то отстаёт, источником правды всё равно остаётся JSON.

## 5. Полный цикл на примере

```bash
# 1. Собрать сайт
cd ~/p/portfolio
npm run build

# 2. Запустить review
pin-note dist --source-dir . --data-dir ./.review

# 3. Оставить комментарии в http://127.0.0.1:4174

# 4. В другом окне попросить агента разобрать .review/comments.json
#    и пересобрать проект

# 5. Проверить результат в браузере
# 6. Остановить PinNote: Ctrl+C
```

Для dev-сервера:

```bash
# 1. Запустить dev-сервер (в своём терминале)
cd ~/p/portfolio
npm run dev

# 2. В другом терминале запустить PinNote поверх него
#    (адрес dev-сервера PinNote найдёт сам; если нет — добавь --target)
pin-note .

# 3. Оставить комментарии в http://127.0.0.1:4174

# 4. Попросить агента разобрать .review/comments.json
#    Пересобирать не нужно: dev-сервер применит правки через HMR.
```

После правок можно оставить новые комментарии и повторить цикл. Старые остаются в JSON со статусами `resolved`, `wontfix` или `orphaned`.

## 6. Режим прокси: работа с dev-сервером

Если проект уже запущен через Vite/Next/Astro, собирать его не нужно:

```bash
cd ~/p/project
npm run dev

# в другом терминале, тоже из корня проекта
pin-note .
```

PinNote сам находит запущенный dev-сервер: смотрит локальные порты, сопоставляет рабочий каталог процесса с папкой проекта и проверяет, что сервер отдаёт HTML. Если сервер один, адрес подставляется автоматически. Если найдено несколько — PinNote покажет список и попросит `--target`.

- Первый аргумент — **корень проекта**, а не папка сборки: оттуда берутся `sourceHints` и туда пишется `.review`.
- Не запускай `pin-note .` из папки самого PinNote: тогда комментарии всех проектов попадут в `~/p/pin-note/.review`. Если ты уже находишься в PinNote, укажи путь явно: `pin-note ~/p/project`.
- У каждого проекта должен быть свой `.review`. Не передавай один и тот же `--data-dir` разным проектам.
- `--target http://localhost:5173` нужен, если автоопределение не сработало, сервер запущен в Docker/WSL или найдено несколько кандидатов. Порт должен совпадать с тем, что напечатал dev-сервер.
- `--no-detect` принудительно отключает поиск dev-сервера и включает статический режим.
- Автоопределение работает на macOS и Linux. На Windows, в Docker/WSL и для dev-серверов с нестандартным рабочим каталогом используй `--target`.
- Открывай Review URL (`http://127.0.0.1:4174`), а не адрес dev-сервера. PinNote проксирует запросы и вставляет клиент в HTML на лету.
- WebSocket и HMR пробрасываются, поэтому правки агента применяются без пересборки. Если HMR не работает, проверь, что dev-сервер слушает тот же хост, на который указывает `--target`.
- API, авторизация, SSR и server components работают как в обычном dev-режиме: PinNote не подменяет приложение, а проксирует его.
- Service worker может перехватывать `/__review/*`; на время review-сессии его лучше отключить.
- Если dev-сервер отдаёт жёсткий CSP, клиент может не загрузиться. Для review ослабь CSP или используй статическую сборку.
- Поддерживается локальный `http://` или `https://` target (для https сертификат должен быть доверенным). Это не прокси для чужих сайтов из интернета.

Если dev-сервер недоступен, PinNote вернёт 502. Запусти его и обнови страницу.

## 7. Если что-то не работает

| Симптом | Причина и решение |
| --- | --- |
| Нет кнопки «Комментировать» | Открыт адрес dev-сервера или `file://`, а не адрес PinNote. Проверь, что в DOM есть `<script data-pin-note>`; посмотри ошибки в консоли. |
| Кнопки нет из-за CSP | Жёсткий CSP может блокировать встроенный клиент. Для review-сессии ослабь CSP или используй сборку без него. |
| В статическом режиме внутренний маршрут отдаёт 404 | Добавь `--spa`. В режиме прокси маршруты обрабатывает dev-сервер. |
| Страница пустая или без стилей | Не та папка сборки или неверный `--target`. Проверь, что в папке есть `index.html`, а dev-сервер отвечает по указанному адресу. Если проект собран с `base: '/sub/'`, для review пересобери его с `base: '/'`. |
| PinNote отвечает 502 | До dev-сервера из `--target` не достучаться. Проверь, что он запущен и слушает тот же хост и порт. |
| Порт отличается от 4174 | Порт занят, PinNote взял следующий. Открой адрес из терминала или задай `-p 4180` явно. |
| Комментарии пропали после сборки | `--data-dir` указывал внутрь `dist`, а сборка очистила папку. Используй `--data-dir ./.review` в корне проекта. |
| В списке комментарии другого проекта | Запусти PinNote из корня нужного проекта или передай его первым аргументом. Проверь путь к `comments.json` внизу панели: у разных проектов не должно быть одного `--data-dir`. |
| Агент не видит комментарии | Проверь фактический путь `--data-dir`: относительный путь считается от папки, где запущен PinNote. |
| Агент обновил статусы, а браузер их не показал | Нажми «Обновить» в панели или перезагрузи страницу. |
| Вкладка не перезагружается после правок | В статическом режиме пересобери проект. В режиме прокси перезагрузку и HMR делает dev-сервер: проверь его консоль и WebSocket. Если запускал с `--no-watch`, обновляй вкладку вручную. |
| HMR/WebSocket не подключается | Проверь, что `--target` указывает на тот же хост и порт, который слушает dev-сервер. Некоторые dev-серверы требуют явно разрешить WebSocket на другом origin. |
| Dev-сервер запущен, но PinNote его не нашёл | Автоопределение работает на macOS/Linux и требует, чтобы рабочий каталог процесса был внутри папки проекта. Для Windows, Docker/WSL или нестандартного запуска укажи адрес через `--target`. |
| Комментарий сохранился только в браузере | Сервер стал недоступен, клиент перешёл в localStorage. Верни сервер, скопируй комментарии кнопкой «Скопировать для агента» и создай их заново. |
| Нужен комментарий к iframe или области canvas | Ограничение версии: iframe не поддерживается, у canvas сохраняется только точка клика, без области и кадра. |
| Кнопка скриншота не работает | Нужен `localhost`/`127.0.0.1` (secure context), запущенный review-сервер и браузер с `getDisplayMedia`. При запросе выбери вкладку с сайтом, а не окно или экран. |
| Скриншот не появился у агента | Проверь поле `screenshot.file` в `comments.json` и файл в `.review/screenshots`; `feedback.md` должен содержать ссылку `![Скриншот](screenshots/...)`. |

## 8. Опции запуска

| Опция | Назначение |
| --- | --- |
| `-p, --port <port>` | Порт review-сервера, по умолчанию `4174`. |
| `--host <host>` | Хост, по умолчанию `127.0.0.1`. |
| `--target <url>` | Явно указать адрес dev-сервера, например `http://localhost:5173`; без него PinNote ищет сервер сам. |
| `--no-detect` | Не искать dev-сервер автоматически, работать как статический сервер. |
| `--data-dir <dir>` | Где хранить `comments.json`, `feedback.md`, `AGENT.md`. По умолчанию `<directory>/.review`; у каждого проекта должен быть свой каталог. |
| `--source-dir <dir>` | Где искать исходники для `sourceHints`. По умолчанию `<directory>`. |
| `--spa` | Отдавать `index.html` для неизвестных HTML-маршрутов (статический режим). |
| `--no-open` | Не открывать браузер автоматически. |
| `--no-watch` | Не следить за файлами, `comments.json` и не перезагружать вкладку. |
| `-h, --help` | Показать справку. |
| `-v, --version` | Показать версию. |

## 9. Ограничения

PinNote делает скриншоты только выбранного элемента, не работает с iframe, не выделяет области canvas/WebGL и не обходит CSP. Прокси работает только с локальным dev-сервером — указанным явно или найденным по папке проекта; инструмент не предназначен для чужих сайтов в интернете. Сервер слушает только `127.0.0.1` и не имеет авторизации — не выставляй его в сеть.

Полный список возможностей и ограничений — в [README.md](README.md).
